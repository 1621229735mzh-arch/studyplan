# 复习导入标准与 JSON 格式 v1

制定日期：2026-10-30。依据本轮确认的“实际学习完成后才建立复习，沿用计划页面组织”。格式检查结果见 [本轮规范验证](../testing/review-import-format-20261030.md)。

**当前交付是格式规范、Schema 和示例；网站复习导入、完成来源导出和导入 API 尚未实现。示例不代表真实学习内容，不应交给现有学习计划导入接口。**

## 1. 用途与基本流程

复习文件只组织已经完成的内容，不能用来提前为尚未学完的计划创建复习任务。

1. 从当前账号数据中核对实际已完成内容及其来源 ID。
2. 在网站外讨论需要纳入复习的内容、日期建议和准备确认的日期，再生成 JSON。
3. 服务端校验文件，并从有效学习记录重新计算实际完成状态与完成日。
4. 展示来源、完成日、建议日、拟安排日以及新增／复用／冲突，供本人核对。
5. 本人确认后，事务内再次检查来源及版本，追加复习内容和明确日安排。

导入文件不产生学习或复习完成记录，不提供用时／预算输入，不设置全局复习间隔。没有 `days` 安排的条目只纳入复习，不进入今日。建议日期到期也不自动进入今日。

## 2. 文件与顶层结构

UTF-8 `.json`，一个 JSON 对象，不包含注释、Markdown 围栏或解释文字。所有层级拒绝未知字段和重复 JSON 键。数字使用 JSON 数字，不能用字符串代替。

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `documentType` | 是 | 固定 `REVIEW_IMPORT`，与学习计划、进度目录的文件区分 |
| `schemaVersion` | 是 | 固定整数 `1`，独立于学习计划导入版本 |
| `reviewPlanId` | 是 | 1—64 位英文字母、数字、下划线或连字符；同一批重试不变 |
| `title` | 是 | 本次复习方案标题，1—200 字符，不能全为空白 |
| `items` | 是 | 至少一条复习来源定义；同一来源只定义一次 |
| `days` | 是 | 需要明确确认的日期安排；只加入内容时为 `[]` |

不设学习计划式的 `startDate/endDate/months/weeks`。复习逐步从已学内容累积，日安排允许稀疏，月／周由实际日安排和复习记录汇总。没有列出的日期不代表休息、取消旧安排或删除历史。

## 3. 复习项 `items[]`

| 字段 | 含义 |
| --- | --- |
| `key` | 文件内唯一引用键，1—64 位英文字母、数字、下划线或连字符 |
| `source` | 一个真实已完成来源，使用下述两种形式之一 |
| `suggestion` | 明确声明不提供建议、相对完成日建议或固定日期建议 |

标题和科目从系统来源读取，文件不重复填写，以免名称相近时错误匹配。`key` 只用于文件内引用，不替代数据库身份。ID 为正整数，最大 `9007199254740991`，避免浏览器数字精度丢失；不得根据标题、位置、题号或别的环境推测 ID。

### 3.1 已完成任务

```json
{"type":"TASK","taskId":900001}
```

表示完整复习该任务对应的内容。v1 接受能够明确判断完成的普通数量任务和按书接续内容段：

- 普通数量任务：有真实有效的首次学习量，累计达到任务明确的总量；仅完成某一天的日安排，不等于完整任务完成。
- 按书接续 `CONTINUED_STUDY`：该段内容的有效 `continuationDelta` 累计达到100%。30%的整段不能通过导入冒充已完成。
- 实际完成日由服务端按记录所属日期、记录ID顺序重算，为有效记录首次累计达到完整内容要求的学习日。只考虑不晚于当前学习日的有效记录。
- 任务存在、处于可用状态且当前仍满足完成要求，才可预览／确认。原参考排期、日历日期、预计结束日期均不是完成证据。

没有明确总量／完成依据的时间型任务、持续计数任务和整份题目序列，v1 不凭“结束当天”、参考题数、文字说明或仅有用时认定整个任务学完。`COUNT_REVIEW/RECAP/CHECK_ONLY` 也不能作为首次学习完成来源。需要按具体题目或更小范围复习时，后续再扩展来源类型；不把部分内容伪装成完整任务。

### 3.2 计划外已学记录

```json
{"type":"AD_HOC_RECORD","sourceRecordId":900002}
```

仅引用没有关联任务的原学习记录，复习范围限于这条记录实际保存的已完成内容：记录未删除、日期不晚于当前学习日、有科目、有正数首次学习量。完成日取原 `recordDate`，不能据此宣称整章或整份资料完成。仅有文字、复盘或历史用时而缺少明确已学范围的记录，v1 不自动判定完成。

有任务关联的记录不能借此类型绕过任务完成校验；应引用已完成的 `TASK`，或等待后续支持具体题目／范围来源。两种来源不可在同一个对象中混填。

## 4. 日期建议 `suggestion`

三种模式互斥，不能省略，也不能填写 null：

| 格式 | 含义 |
| --- | --- |
| `{"mode":"NONE"}` | 不提出新建议；新内容保留无建议日期，已有内容不清空原日期 |
| `{"mode":"AFTER_COMPLETION","offsetDays":3}` | 建议日期＝服务端实际完成日＋指定整数天数 |
| `{"mode":"ON_DATE","date":"2026-11-05"}` | 本人已选择的固定建议日期，不能早于实际完成日 |

`offsetDays` 是这次文件明确提供的参数，不是系统默认间隔。允许0表示同一学习日完成后复习；不允许负数、小数或日期加法溢出。未确定间隔就使用 `NONE`，不能自动补成1／3／7天或套用记忆曲线。

建议可以已经到期：保留原建议日及到期信息，不能自动改为今天。固定建议日不随原学习计划参考日期变化。实际记录变化导致完成日变化时，旧预览失效，重新计算后再确认。

`AFTER_COMPLETION` 始终以首次实际学完该来源的日期为起点，不是以上一次复习日为起点。后续“不会／模糊／掌握”产生的日期建议继续由原复习反馈业务处理；本格式不定义多轮间隔脚本。

**三种建议模式均不产生日安排。** 要在某天执行，必须另写 `days` 并在预览中明确确认。实际安排可以不同于建议日，服务端分别显示二者，不擅自替本人决定。

## 5. 日安排 `days[]`

```json
{"date":"2026-11-05","items":[{"reviewKey":"completed-content"}]}
```

- `date` 为真实 `YYYY-MM-DD`；当前学习日按北京时间每天09:00切换。明确填写的日期不再次偏移。
- v1 新增待执行安排只能在当前或未来学习日，且不得早于来源实际完成日。历史补记复习记录是独立用例，不能通过安排文件导入完成历史。
- 同一日期只能出现一次，每个日对象至少一项；没有安排的日期省略，无需填休息日。
- `reviewKey` 必须引用本文件 `items[].key`。同一 `key` 在整个 `days` 中最多出现一次，符合当前每项一个待执行日期的模型。
- 可以有未被 `days` 引用的 `items`，表示只纳入复习；不能有未定义的日引用。
- 不允许通过多个key、重复来源或多份文件同时为同一内容建立多轮待执行日期。完成后再安排下一次；多轮并行排期另行设计。
- 日、周、月都使用这一份确认安排；确认本身不产生完成量或掌握反馈。

## 6. 已有内容与数据保护

来源身份按 `TASK + taskId` 或 `AD_HOC_RECORD + sourceRecordId` 确定，不按文件key或标题确定。

| 当前情况 | v1 处理 |
| --- | --- |
| 尚未加入复习且来源满足完成要求 | 新建复习项；建议与日安排按文件和确认结果应用 |
| 已有同来源复习项、未归档 | 复用原身份与历史，不新建第二项 |
| 请求建议与已有建议相同，或 `NONE` 不提出新建议 | 保留原值，可继续检查日安排 |
| 新建议与已有非空建议不同 | 整份预览报冲突，不能借导入覆盖；改为 `NONE` 或经正常业务入口调整 |
| 已有内容建议为空，文件提出新建议 | 预览明确列出新增建议，确认后补充，仍检查版本 |
| 已安排在同一天 | 标示已有相同安排，不重复写入 |
| 已安排在另一天 | 整份预览报冲突；通过正常日期调整入口处理后重新预览 |
| 同一天已经完整复习过 | 不再创建该日待执行安排 |
| 来源失效、尚未完成或复习项已归档 | 整份拒绝，不恢复／重建／静默跳过 |

不导入掌握反馈、完成比例、学习数量、实际完成日、历史复习次数或用时。文件不能携带密码、会话、模型密钥或SQL。导入不会修改学习计划、学习记录、课程目录、全局间隔和已有复习记录；`items` 中没出现的旧内容继续保留。

后续修改／删除来源学习记录不能自动删除已有复习痕迹；新的导入必须重新核验当前完成状态。更广泛的来源变更处理不由格式文件擅自决定。

## 7. 预览、确认、防重与事务

以下是将来实现导入时的约束，不是当前已经可调用的接口行为。

- **整份校验**：JSON形状、真实日期、来源身份与完成状态、引用唯一性、日期顺序和已有状态均通过才可确认。结构校验成功不代表来源存在或已经完成。
- **明确预览**：逐项显示来源标题、科目、来源ID、当前完成依据、实际完成日、建议日、拟安排日，以及新增／复用／新增建议／已有相同安排／冲突。先列加入清单，再单独列会进入日期安排的条目；本人明确确认后才写入。
- **不部分应用**：存在任一错误或冲突时整份不能确认。不静默略过未学完的项目，也不把未学完项目保存成将来自动触发的复习。
- **绑定预览**：预览令牌绑定当前账号、原始文档摘要、来源完成依据及版本、相关复习项和当天复习记录状态，并返回 `expiresAt`。修改文件、数据变化、预览过期或跨09:00学习日切换，都要求重新预览。不能由文件自行提供“完成版本”替代实时核验。
- **事务确认**：在锁定来源和复习安排上下文后，通过学习／复习业务服务重新校验并一次性应用。导入服务不能绕过业务服务直接修改其他模块Mapper；失败回滚，不留半份清单或日安排。
- **方案防重**：账号内相同 `reviewPlanId` 或相同业务内容指纹的新预览拒绝重复导入，并返回已导入批次信息。换ID、改标题、更换本地key、重新排列数组不能绕过相同业务内容校验。
- **内容指纹**：将文件内引用解析为真实来源后，对来源、建议模式与参数、明确安排日期排序并生成规范化指纹；不把方案ID、标题或局部key当作不同业务内容。原始文档摘要另用于绑定本次预览，不能替代语义防重。
- **确认重试**：原文档和同一个已成功确认的令牌只返回原结果，不重新应用。变更文档不能复用令牌；新一次预览也不能绕过已导入方案校验。既有来源可用于不同日期的后续复习，但不得覆盖尚未执行的旧安排。
- **只读预览**：允许保存预览元数据；预览不会创建复习项、日安排、学习记录或复习完成记录。离线不能预览／确认。

后续预览／确认接口应独立位于复习模块，例如 `POST /api/review/imports/preview` 和 `/confirm`；请求携带原始 `document` 字符串，确认另带 `previewToken`。使用原始文本以检查重复JSON键，保留登录、CSRF、提交防重和失败输入。**这两个路径目前尚未实现。**

## 8. Schema 与业务校验的分工

[review-import.schema.json](review-import.schema.json) 使用 JSON Schema Draft 2020-12，校验字段、类型、枚举、互斥分支、基本格式和禁止额外字段。调用方需启用真实日期格式校验；仅正则不能识别2月30日。

服务端还必须检查：重复JSON键、空白标题、日期是否在可表示范围、日期加法是否溢出、重复key／来源／日期、引用存在性、跨日重复安排、来源权限及完成状态、完成日、已有安排冲突、防重、过期和并发。Schema无法单独验证这些条件，不允许客户端据此直接写库。

v1 不设置每日复习内容上限或时间预算。实现时的文件体积与请求负载限制属于接口保护，需另在实际接口文档中公开，不能解释成个人学习额度。

## 9. 两个格式示例

- [只加入复习](review-import-pending-example.json)：`suggestion.mode=NONE`，`days=[]`，表示不提出新日期、不安排到今日。
- [加入内容并明确安排其中一项](review-import-example.json)：一个来源按实际完成日＋3天提出建议，并明确安排到某天；另一来源只加入清单。

两份示例的900001／900002均为虚构ID，不能假设目标账号有这些数据。第二份示例的讲解前提为“测试来源在2026-11-02实际完成、预览学习日不晚于2026-11-05”，所以相对建议与日安排都为11月5日。这只是条件示范，不是用户的真实完成日期、复习内容或已批准间隔；更换来源后必须重新计算并核对日期。

## 10. 给外部 AI 的提示词

> 根据我提供并核对过的已完成来源清单，按 review-import.schema.json 输出一个 REVIEW_IMPORT v1 JSON，不加注释或Markdown围栏。
>
> 只使用清单中真实来源ID，不猜ID、不按计划日期认定完成，不把部分进度当完整内容。来源清单不完整或无法证明完成时先指出缺项，不生成假数据。
>
> items 只引用来源，科目与内容标题由网站解析。未确定日期建议时明确填 suggestion.mode=NONE；只有我明确选择间隔时才填写 AFTER_COMPLETION，起点是清单中的实际完成日，不是原计划日期。建议不会自动加入日期安排。
>
> 只有我明确同意安排的内容才写入 days，其余保留在items；一个来源最多一个待执行日期，不生成以后自动触发的未学内容，不填写学习量、完成比例、掌握反馈或时间预算。逐项核对已有安排，不能覆盖旧日期。更换文件局部key不等于新内容。
